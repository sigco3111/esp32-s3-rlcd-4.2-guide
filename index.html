Waveshare ESP32-S3 4.2인치 RLCD 보드 브링업 실전 기록

초보자가 반드시 부딪히는 12가지 함정과 해결법

sigco3111 2026-10-30 읽기 약 12분
이 문서의 원칙

기록된 값은 실측된 값만 적었습니다. 문서화되지 않은 항목은 확인 필요 로 표시했습니다. 공유기 비밀번호, 관리자 비밀번호, Wi-Fi PSK 같은 인증 정보는 어떤 형태로도 기록하지 않았습니다.

개요

Waveshare ESP32-S3 4.2인치 RLCD 보드를 새로 산 뒤, 전원 넣고 화면이 켜지는 것까지 약정된 순서를 따랐더니 거의 모든 단계에서 막혔습니다. 이 글은 그 막힌 지점들을 왜 막혔는지, 어떻게 판별했는지를 중심으로 정리한 브링업 기록입니다.

TL;DR로 압축하면 이렇습니다.

  • macOS에서 Python 도구 설치는 pipx 와 brew 를 분리해야 합니다.
  • Wi-Fi reason=201 은 비밀번호 오류가 아니라 AP를 못 찾았다는 뜻입니다.
  • USB에서 디바이스가 조용히 사라지면, 먼저 전원을 완전히 끊었다가 다시 넣으세요. 대부분 여기서 끝납니다.
  • 측정 도구가 대상을 바꿔버리는 경우가 있습니다. esptool read-mem 의 GPIO0 판정 사례가 전형적입니다.
잘된 것
  • esptool 4종 명령으로 칩/Flash/보안/MAC 확인
  • IDF v5.5.5 로 공식 예제 빌드 및 플래시
  • SHTC3 온습도 실측 로그 확보
  • CDC-ACM 10/10 왕복 통신 검증
  • USB CDC 합성 디바이스 macOS 정상 열거
막힌 것
  • macOS pip 부재와 PEP 668 차단
  • brew/pipx PATH 우선순위 충돌
  • Wi-Fi reason=201 을 잘못 해석
  • 동기 스캔으로 인한 스캔 0개 오판
  • USB 열거 조용한 실패 (DWC2 엔드포인트)

esptool이 brew 버전(5.6.0)과 IDF 내장 버전(4.12.0) 두 개 깔려 있으면 어느 쪽이 실행되는지에 따라 명령 문법과 출력이 달라집니다. 작업 시작 전에 which -a esptool 과 esptool version 으로 확정하세요.

진행 순서

아래 8단계 순서대로 진행했습니다. 각 단계의 막힌 지점은 뒤의 함정 목록과 1:1로 대응합니다.

1. 구매 직후 하드웨어 확인

첫 단계는 화면을 켜는 것이 아니라, 무엇이 들어있는지 확인하는 것입니다. esptool 4종 명령이면 충분합니다.

bash
esptool --chip esp32s3 chip-id
esptool --chip esp32s3 flash-id
esptool --chip esp32s3 get-security-info
esptool --chip esp32s3 read-mac
명령알 수 있는 것이 보드에서 확인된 값
chip-id칩 종류와 리비전ESP32-S3 rev v0.2
flash-idFlash 제조사와 용량16MB
get-security-infoSecure Boot / Flash Encryption 상태둘 다 비활성
read-mac공장 출하 MAC28:84:85:xx:xx:xx (마스킹)

get-security-info 에서 두 항목이 모두 비활성인 것은 일반적인 상태입니다. 그럼에도 확인해야 하는 이유는, "이 보드가 지금 flash lock 상태인가"를 미리 알아야 이후 백업/복구 전략을 세울 수 있기 때문입니다.

2. macOS 개발환경 구축

이 단계가 전체 작업에서 가장 오래 걸렸습니다. IDF 설치 자체보다 PATH와 Python 관리에서 문제가 터졌습니다.

bash
# 1) 시스템 python 확인. macOS 기본 python은 Xcode 것이라 pip 바이너리가 없다.
python3 -V
python3 -m pip -V          # pip 자체가 없거나 외부 관리 환경이라 차단될 수 있다

# 2) Homebrew python 설치 (pip 은 libexec/bin 에 들어간다)
brew install python

# 3) 개별 도구는 pipx 로 격리 설치
brew install pipx
pipx install esptool
pipx install pre-commit

# 4) IDF 의 ccache 를 켜고 컴파일
export IDF_CCACHE_ENABLE=1

그래도 pip: command not found 가 남으면, Homebrew python의 pip 은 bin/ 이 아니라 libexec/bin/ 에 있다는 사실을 확인하세요.

주의

IDF의 export.sh 를 그냥 소스하면 셸이 아닌 다른 python venv를 찾아버릴 수 있습니다. 설치 시점의 python과 셸의 python이 달라진 상황이며, 이때는 venv 경로를 명시하는 wrapper 스크립트를 씁니다.

3. 출고 펌웨어 백업과 부팅 로그 읽기

새 보드에는 출고 펌웨어가 이미 들어있습니다. 덮어쓰기 전에 반드시 전체 영역을 백업해 두세요. 나중에 "뭘 날렸지"가 되면 복구가 불가능합니다.

bash
# 전체 Flash 덤프 (16MB)
esptool --chip esp32s3 read_flash 0x0 0x1000000 backup_16mb.bin

# 백업본 해시 확인
shasum -a 256 backup_16mb.bin

백업 이후 부팅 로그를 읽습니다. 시리얼 모니터로 붙여서 재부팅하면 ROM 부팅 로그(라틴어 0x0B 리셋 사유, 칩/Flash 정보)와 애플리케이션 로그가 이어서 나옵니다. 이 로그에서 rst:0x15 (USB_UART_CHIP_RESET) 가 보이면 부팅이 아니라 다운로드 모드로 진입한 것이므로, 뒤에서 설명하는 전원 차단 복구가 필요합니다.

백업 파일 크기와 해시, 그리고 백업에 걸린 시간은 기록해 두세요. 복구 시점에는 어떤 백업을 쓸지 판단하는 근거가 됩니다. (이 문서의 백업 파일 해시값 자체는 확인 필요)

4. 공식 예제 빌드·플래시

워크스페이스에 포함된 공식 예제 두 개를 실제로 빌드해서 플래시했습니다. 05_I2C_SHTC3 과 09_LVGL_V9_Test 입니다.

bash
cd /path/to/05_I2C_SHTC3
idf.py set-target esp32s3
idf.py build
idf.py -p /dev/cu.usbmodem101 flash monitor

SHTC3 예제에서 온습도가 실제로 들어오는 로그가 관측됐습니다.

log
RH:20.70%, Temp:30.50°C

이 로그가 나온다는 것의 의미가 큽니다. GPIO13/GPIO14 배선, I2C 주소 0x70, 센서 전원까지 모두 정상이라는 뜻입니다. 화면이 안 뜬다고 I2C까지 의심할 필요를 없애줍니다.

플래시 완료 시 esptool이 검증 결과를 출력합니다.

log
Hash of data verified.
Hash of data verified.
Hash of data verified.
Done

Hash of data verified 가 3회 나오는 것은 app, bootloader, partition 테이블 영역을 각각 검증한 결과이며, 정상 동작입니다.

5. Wi-Fi STA 연결 실패 진단

STA 연결이 반복해서 실패하고 로그에 reason=201 이 떴습니다. 처음엔 비밀번호 오류라고 생각했는데, 이 해석이 완전히 틀렸습니다.

log
wifi:sta: disconnecting from ...
wifi: sta: reason 201 (NO_AP_FOUND)

201은 NO_AP_FOUND, 즉 "목표 SSID를 스캔 목록에서 못 찾았다"는 의미입니다. 비밀번호 오류는 다른 reason 코드로 나옵니다. 이 구분을 모르고 20분 넘게 PSK를 만지작거리느라 시간을 버렸습니다.

원인 1: country code 미설정

기본 country code가 US 로 잡히면 12/13채널을 못 쓰는 지역 제한이 걸립니다. 로그에서 nchan=13 인 채널이 보인다면 그것이 단서입니다.

c
esp_wifi_set_country_code("KR", false);

원인 2: 스캔과 연결의 충돌

STA 연결 중에 동기 스캔을 끼워 넣으면, 스캔 결과가 0개인 것처럼 보여 "공유기가 없다"로 오판하게 됩니다. 스캔은 별도의 FreeRTOS task로 분리해야 합니다.

c
// 연결 루프와 스캔을 서로 다른 task로 분리
xTaskCreate(scan_task, "wifi_scan", 4096, NULL, 5, NULL);

6. 2.4GHz AP가 없는 환경, USB CDC-NCM / CDC-ACM 대체 회선

주변에 2.4GHz AP가 없는 환경에서는 STA 회선을 테스트할 수 없습니다. 이때 회선을 USB로 대체합니다.

회선성격적합한 용도
USB CDC-ACM가상 시리얼. 트랜스포트에 의존하지 않음AT 명령, 상태 조회, 제어 채널
USB CDC-NCMUSB 위 이더넷. IP 계층을 그대로 제공TCP/UDP 소켓 테스트

이 보드 주변에서 관측된 2.4GHz AP 실측 목록은 다음과 같습니다. SSID는 기록해 두었지만 인증 정보(PSK)는 기록하지 않았습니다.

SSID채널비고
telecopCH12.4GHz AP 존재 확인
hiddenCH7, -36dBmhidden SSID, WPA2-PSK
A1ASSETCH10 / CH112.4GHz AP 존재 확인
Galaxy Jump2 4304CH62.4GHz AP 존재 확인
대역 불일치

Mac이 붙어 있던 SSID는 5GHz (Channel 64, 802.11ax) 였습니다. ESP32-S3는 2.4GHz 전용이므로 그 SSID에는 애초에 붙을 수 없습니다. "왜 안 붙지"를 설명하는 가장 단순한 답이며, 이것을 먼저 확인하면 다른 추론이 불필요해집니다.

7. USB 열거 실패 3분류와 복구

USB는 "된다/안 된다"가 아니라 세 가지로 갈립니다. 분류를 먼저 하면 복구 경로가 정해집니다.

분류증상복구
1. PHY 점유 기존 JTAG 콘솔이 사라짐 (TinyUSB가 USB PHY를 점유) 콘솔을 UART로 전환
2. 다운로드 모드 진입 rst:0x15 (USB_UART_CHIP_RESET), boot:0x3 로 고정 전원 완전 차단 후 재투입 (유일한 해법)
3. 디스크립터 충돌 CDC+NCM 동시 활성화로 디바이스가 아예 사라짐 하나만 켜기

3번 분류의 호스트 로그에서는 단계적으로 실패가 드러납니다. 디바이스 쪽 로그가 0건인 것이 핵심 단서입니다.

log
setAddress: result code 4
createDevice: failed
# 이후 포트가 영구 비활성

호스트 로그에 setAddress: result code 4 가 나오면 디바이스가 주소를 받지 못한 것입니다. 이때 read-mem 로 GPIO0을 확인하려 들면 오히려 상황을 망칩니다(함정 14 참조).

8. 전체 정리 + 다음 단계

전체 흐름을 되돌아보면, 실패의 원인은 크게 두 갈래입니다. 도구 관리 문제(Python, PATH, 버전)와 하드웨어/드라이버 제약(대역, USB PHY, 엔드포인트 수)입니다. 전자는 문서로 해결이 되고, 후자는 설계 제약이라 시간을 낭비하는 지점입니다.

다음 단계
  • USB CDC-ACM 위에 실제 제어 명령을 얹기
  • STA 회선을 2.4GHz AP가 있는 환경에서 재검증
  • RLCD 패널의 실제 표시 테스트 (확인 필요)
  • LVGL V9 예제 화면 확인 (확인 필요)
환경 정리 규칙
  • 도구 설치 경로는 단일 원칙으로 (brew 또는 pipx)
  • esptool / IDF 버전은 스크립트 시작 시 고정
  • ccache 는 IDF_CCACHE_ENABLE=1 로 항상 켜기
  • IDF 는 wrapper 스크립트로만 로드

함정 12가지

각 항목은 증상 / 원인 / 처방 구조입니다.

01

pip: command not found

함정
증상
pip install 을 치면 pip: command not found.
원인
macOS 기본 python은 Xcode 소유이고 pip 바이너리가 없습니다. Homebrew python을 설치해도 pip은 bin/ 이 아니라 libexec/bin/ 에 들어갑니다.
처방
brew install python 후 python3 -m pip -V 로 경로를 확인합니다. 브라우저에 libexec/bin/pip3 가 보이는데 PATH에 없으면 추가하거나, 가능하면 pipx 경로를 씁니다.
02

brew python이 새 버전 끌고 오면 /opt/homebrew/bin/pip3 링크가 뒤집힘

함정
증상
어제까지 되던 pip3 가 갑자기 다른 버전의 pip를 가리킵니다.
원인
brew가 새 python 버전을 끌어오면서 /opt/homebrew/bin/pip3 심볼릭 링크의 대상이 교체됩니다.
처방
python3 -V 과 pip3 -V 를 항상 대조합니다. 두 명령이 서로 다른 python을 가리키면 즉시 판단 가능합니다.
03

externally-managed-environment (PEP 668)

함정
증상
pip install 이 externally-managed-environment 오류로 차단됩니다.
원인
PEP 668. 시스템/brew python을 직접 수정하지 못하도록 표준이 바뀝니다.
처방
pipx install <tool> 을 씁니다. --break-system-packages 는 쓰지 않습니다. OS가 통째로 깨집니다.
04

brew와 pipx에 같은 도구가 중복 설치됨

주의
증상
어떤 명령이 어떤 버전인지 알 수 없게 됩니다.
원인
PATH 우선순위. brew의 /opt/homebrew/bin 와 pipx의 ~/.local/bin 순서가 shell마다 다릅니다.
처방
한쪽만 유지합니다. which -a <tool> 로 실제 해석 순서를 확인하고, 중복은 제거합니다.
05

brew install ninja-build 실패

함정
증상
brew install ninja-build 가 "No available formula" 로 실패합니다.
원인
formula 이름이 ninja 입니다. ninja-build 는 실제 이름이 아닙니다.
처방
brew install ninja. brew는 transaction이라 하나의 formula가 틀리면 묶인 설치 전체가 롤백되므로, 한 번에 하나씩 확인하며 진행합니다.
06

export.sh 가 다른 python venv를 찾음

함정
증상
IDF를 켰는데 idf.py 가 에러를 냅니다. 로그에 예상 못한 venv 경로가 보입니다.
원인
설치 시점의 python과 셸에서 sourcing하는 시점의 python이 다릅니다. export.sh 는 그 시점의 활성 python을 따라갑니다.
처방
wrapper 스크립트를 만들어 venv 경로를 명시합니다. 예: source ~/esp/esp-idf/export.sh 를 감싼 ~/esp/activate-idf.sh 를 만들고, 그 안에서 IDF_PYTHON_ENV_PATH 를 고정합니다.
07

idf.py set-target 가 ccache를 끔

주의
증상
재빌드 시간이 ccache 적용 전 수준으로 되돌아갑니다.
원인
set-target 은 툴체인/SDK 설정을 새로 잡는 단계라 ccache 설정이 초기화됩니다.
처방
export IDF_CCACHE_ENABLE=1 을 IDF 로드 이후, set-target 이전에 다시 설정합니다. 이 환경에서는 재빌드 14초, 히트율 49.9% 로 측정됐습니다.
08

Wi-Fi reason=201 을 비밀번호 오류로 오해

함정
증상
PSK를 여러 번 고치면서도 연결이 안 됩니다.
원인
reason=201 은 NO_AP_FOUND 입니다. "AP를 못 찾았다"는 뜻이지, "인증이 실패했다"는 뜻이 아닙니다. 스캔 목록에 목표 SSID가 없으면 공유기 문제입니다.
처방
연결 시도 전에 스캔으로 목표 SSID가 보이는지 확인합니다. 안 보이면 PSK를 만지작거리지 말고 공유기와 대역을 점검합니다.
09

country code 미설정으로 12/13채널 제한

주의
증상
13채널 AP가 스캔 목록에 나타나지 않습니다. 로그에 nchan=13 이 보입니다.
원인
country code가 기본값(US) 상태라 해당 채널이 제한됩니다.
처방
esp_wifi_set_country_code("KR", false); 를 STA 시작 전에 호출합니다. 두 번째 인자 false 는 채널 제한 완화를 뜻합니다. 로그에서 nchan=13 으로 실제 적용을 확인하세요.
10

STA 연결 중 동기 스캔, 스캔 0개 오판

주의
증상
연결 루프 중간에 끼워넣은 스캔이 항상 0개를 반환합니다. "주변에 AP가 없다"로 잘못 판단.
원인
연결 상태에서 동기 스캔을 호출하면 스캔 결과가 신뢰 불가 상태로 반환됩니다.
처방
스캔을 FreeRTOS task로 분리해 별도 스택에서 실행합니다. 또는 STA 연결과 AP 스캔을 서로 다른 단계로 완전히 분리합니다.
11

TinyUSB CDC+NCM 동시 활성화로 USB descriptor 충돌

함정
증상
디바이스가 아예 사라집니다. 드라이버에 잡히지도 않고, 로그도 안 남습니다.
원인
USB CDC 와 NCM 을 동시에 활성화하면 디스크립터가 충돌합니다.
처방
하나만 켭니다. CDC-ACM 과 CDC-NCM 은 동시 사용이 아니라 선택입니다. 필요한 회선 하나만 컴파일 플래그로 남깁니다.
12

DWC2 ep_in_count=5 하드웨어 인위적 제한

함정
증상
USB 열거가 "조용히" 실패합니다. 디바이스 쪽 로그가 0건입니다.
원인
DWC2 하드웨어의 인위적 제한으로 IN 엔드포인트가 5개로 제한됩니다. TinyUSB 컴포넌트의 ep_in_count 설정이 이를 넘어가면 열거 단계에서 멈춥니다.
처방
ep_in_count 를 7로 패치합니다. 호스트 로그에서 실패가 순서대로 드러납니다: setAddress: result code 4 → createDevice: failed → 포트 영구 비활성.

추가 함정: USB 복구 편

USB 문제에서 파생된 추가 항목 6가지입니다. 13~18번은 USB 열거 실패를 다루면서 함께 발견한 내용입니다.

13

rst:0x15 (USB_UART_CHIP_RESET) 은 GPIO0 스트랩과 무관

함정
증상
BOOT 버튼을 눌러도, 떼도, RTS/DTR 어떤 시퀀스를 쓰든 다운로드 모드(boot:0x3)를 빠져나올 수 없습니다.
원인
이 리셋 사유는 GPIO0 스트랩과 무관하게 USB 다운로드 경로를 강제합니다.
처방
유일한 해법은 전원 완전 차단 후 재투입입니다. USB 케이블만 뽑는 것은 전원이 남아 있을 수 있어 부족합니다.
14

read-mem 0x60000004 로 읽은 GPIO0은 항상 0

함정
증상
esptool read-mem 0x60000004 로 GPIO0 레지스터를 읽으면 값이 예외 없이 0입니다.
원인
esptool이 DTR로 GPIO0을 LOW로 끌어내리기 때문입니다. 측정 도구가 대상을 바꾼 것입니다. 그래서 0이 나올 수밖에 없습니다.
처방
판정 근거는 "디바이스가 계속 다운로드 모드에 머무는 현상" 자체입니다. GPIO0 읽기 값으로 판정하지 않습니다.
15

TinyUSB가 USB PHY를 점유, 기존 JTAG 콘솔 사라짐

주의
증상
소스 수정 전에는 JTAG 콘솔로 붙었던 로그가 사라집니다.
원인
TinyUSB가 USB PHY를 점유하면서 기존 디버그 콘솔 경로가 밀려납니다.
처방
콘솔을 UART로 전환합니다.
16

컴포넌트 매니저가 prerelease 버전을 못 찾음

함정
증상
요구 버전이 ^2.0.1~1 인 컴포넌트를 컴포넌트 매니저가 찾지 못합니다.
원인
레지스트리에 해당 버전이 실제로 존재해도, prerelease 표기(~1)를 해석하지 못해 실패합니다.
처방
직접 다운로드해 components/ 에 벤더링합니다. esp_tinyusb 와 upstream tinyusb 둘 다 필요합니다.
17

IDF 5.5 lwIP API 변화

주의
증상
lwIP를 직접 다루는 코드가 컴파일되지 않습니다.
원인
lwIP API 시그니처가 바뀌었습니다.
처방
다음처럼 대응합니다.
  • netif_output_fn(netif, pbuf, ipaddr) : 3인자
  • netif->input 은 (pbuf, netif) 순서
  • netif_get_addr 는 없음
  • 주소 타입은 ip4_addr_t 사용
  • IP 문자열 길이는 IP4ADDR_STRLEN_MAX
18

lwIP 컴포넌트 이름과 esp_timer.h 의 분리

주의
증상
헤더를 못 찾았다거나 컴포넌트를 못 찾는다는 컴파일 에러가 납니다.
원인
lwIP 컴포넌트 이름은 esp_lwip 가 아니라 lwip 입니다. 또한 esp_timer.h 는 별도 컴포넌트라 REQUIRES esp_timer 를 명시해야 합니다.
처방
CMakeLists 의 REQUIRES 에 lwip 와 esp_timer 를 함께 넣습니다.
